# Серверное хранение исследовательских замеров — PROPOSED

## Решение ещё не реализовано

Пользователь предложил добавить сбор в серверное хранение CoreTeams. Это технически возможно, но данный файл — предложение для согласования, **не действующий API или подключённая аналитика**. Текущий клиент сохраняет данные локально и предлагает ручной экспорт. Никаких автоматических загрузок или серверных изменений в этой итерации нет.

## Разделение данных и доступа

- Продуктовые проекты/исходные файлы/Run/артефакты остаются в своём контуре. Исследование — отдельные сущности `study`, `research_session`, `research_event`, `baseline_step`, связанные разрешёнными IDs без копирования содержимого задач.
- `study` задаёт владельца исследования, доступ исследователя, цель, утверждённый срок хранения и правила экспорта/удаления. Авторизованный участник видит/передаёт только разрешённую ему сессию; исследователь — только назначенное исследование, не данные всей команды. При работе по приглашению нужен отдельный ограниченный токен, а не секрет в VITE-конфигурации.
- Псевдоним, код задачи и technical IDs — связываемые данные, не обещание полной анонимности. Таблица контактов, если вообще нужна, хранится отдельно с ещё более узким доступом. Текущий журнал её не содержит.
- `baseline/prototype/interface`, build/environment, consent-version/time, интервалы, структурированные шаги/барьеры/итоги, оценки и allowlisted события соответствуют [текущей схеме](journey-metrics.md). Не принимать произвольные поля, тексты промтов/ответов/результатов, имена/байты файлов, исходные ссылки или контакты.

## Согласие перед передачей

Текущее `journey-local-v1` относится к локальному хранению; **оно не разрешает незаметно загрузить старые журналы на сервер**. Перед серверным сбором нужно показать место хранения, круг доступа, цель, срок, экспорт/удаление и получить отдельное подтверждение обновлённого текста согласия. Согласование принадлежит владельцу исследования, реализация и проверка — команде.

## Предлагаемые операции (пути/API согласовать с gateway)

1. Создать/зарегистрировать сессию в разрешённом исследовании: server study/session ID, client-session UUID, phase, безопасные коды, schema/build/environment, consent version/time. Сервер проверяет права и возвращает подтверждение **после** записи.
2. Дозагрузить пачку событий и интервалы/шаги с ключом идемпотентности. Событие имеет стабильный UUID; уникальность `(study_id, session_id, event_id)` защищает от дублей. Изменяемые шаги/снимок сессии используют ревизию и optimistic concurrency; конфликт не перезаписывает чужую версию.
3. Подтвердить отдельные записанные event IDs и ревизию после завершённой транзакции. `server_received_at`/`persisted_at` хранятся отдельно от клиентских `at` и не подменяют время выполнения задачи. HTTP200 без подтверждения конкретной записи недостаточно для статуса «синхронизировано».
4. Получить свои сессии/исследовательский список и выгрузку, применяя авторизацию на каждой операции и фильтрацию study/tenant. Сопоставление — одинаковый участник/задача плюс явная проверка сопоставимости; не автоматический выбор «лучшей» попытки. Fixture/UI-only/пропуски/незавершённость сохраняют ограничения текущего клиента.
5. Отозвать согласие/удалить сессию и связанные события/шаги/копии в пределах согласованной политики. Повтор удаления идемпотентен. Выгруженные ранее внешние копии обрабатывает ответственный отдельно; сервер не может обещать их автоматическое удаление.

## Клиентская очередь и состояния

`локально → ожидает отправки → отправлено, запись не подтверждена → подтверждено сервером`; отдельно `ошибка`, `конфликт`, `нет согласия/доступа`. Локальный таймер не зависит от доступности сети. Повтор использует те же IDs, очереди не теряются при reload. Уход со страницы не означает отказ от задачи и не гарантирует последнюю сетевую запись.

После подтверждения сервера локальная копия очищается только по согласованной политике, не автоматически по факту fetch. При отзыве согласия во время offline нужно удалить локальный payload, остановить дальнейший сбор и сохранить минимальную адресную операцию удаления до серверного receipt; иначе простая очистка браузера оставит удалённую копию на сервере. Это ещё не реализовано в локальном-only клиенте.

## Приёмка интеграции и владельцы для согласования

- Арина: сущности/транзакции/receipt, доступ, срок хранения, экспорт/удаление и восстановление. Дима: gateway/auth/совместимый API/ошибки/idempotency/CAS. Филипп: развёртывание, доступ исследователя и резервирование по согласованной политике. Катя: цель, согласие/приватный канал, правила сопоставления и интерпретация. Это предложение распределения проверки, не новая назначенная задача или отправленное сообщение.
- Проверить end-to-end на обезличенном fixture: повторная пачка без дублей; offline/reload; ошибка/конфликт; запрет чужого исследования; отсутствие скрытых полей; согласие не переносится автоматически; серверный список/экспорт совпадают с клиентом; удаление с online/offline подтверждается; временные метки не смешиваются.
- Только после этих проверок включать в UI серверную передачу и правдиво менять текст локального хранения. Реальная исследовательская сессия отдельно требует согласия; технический тест не доказывает пользовательскую пользу.
