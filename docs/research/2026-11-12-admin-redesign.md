# Журнал исследования: переработка админки

**Дата:** 2026-11-12. **Текущий статус:** дизайн APPROVED пользователем («Утверждаем»); разрешена подготовка плана, не реализация. Исторические статусы ниже относятся к моменту записи; актуальное общее решение — §6.2.

Это исторический журнал для защиты проекта, не сам дизайн и не implementation plan. До §6.2 рекомендации не считались принятыми; общее одобрение теперь зафиксировано в §6.2. Реализация в этой сессии не разрешена.

## 1. Цель и проблема

Исходная постановка пользователя:

- Нужен единый сайт с общим header, а не отдельный интерфейс с переходом «Интерфейс CoreTeams». Администрирование доступно только администраторам (admin-only).
- Нужны полезные метрики, выбранные после инвентаризации доступных данных и обязательного согласования с пользователем. Текущая диаграмма, по мнению пользователя, бесполезна; это оценка потребности, а не доказательство ошибки вычислений.
- Исходно пользователей предлагалось вынести на отдельную страницу с управлением блокировкой входа и доступом к моделям. Последующее уточнение пользователя (§6): в первой версии достаточно AI-заморозки/снятия; полный бан аккаунта, блокировка входа и отзыв auth-сессий исключены из scope. Исходная формулировка сохранена как история, не как актуальное требование блокировки входа.
- Исследовать токены и стоимость по данным proxy/harness вместо использования времени как основы оценки расхода.
- API equivalent — не реальные расходы подписки. Предположение пользователя «$100/5h» не проверено и не является фактом о тарифе или лимите.
- Фасилитатор делегирует исследования и реализацию, сохраняет координацию и согласование. До одобрения дизайна код не меняется.

**Не входит в текущий этап:** изменение кода, окончательный выбор метрик, архитектуры или тарифной модели; коммиты, push и дальнейшие переключения веток. Отдельные продуктовые правила AI-заморозки согласованы в §6, но дизайн целиком не одобрен. Полный бан аккаунта, блокировка входа и отзыв auth-сессий исключены из первой версии.

### 3.3. Внешние источники: usage, кеш и подписка

По отчёту внешнего исследователя, полные страницы через WebFetch недоступны; получены лишь поисковые выдержки официальных источников. **Это не полная проверка актуальных условий или тарифов.** Автор журнала страницы самостоятельно не проверял.

Источники исследователя:

- [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
- [Pricing](https://platform.claude.com/docs/en/about-claude/pricing).
- [How do usage and length limits work?](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work).
- [What is the Max plan?](https://support.claude.com/en/articles/11049741-what-is-the-max-plan).

В доступных выдержках оснований фиксировать «$100 API equivalent / 5h» не найдено. Лимит подписки и долларовый API equivalent — разные сущности; конвертация между ними не установлена. Эти источники о Claude subscription/Max сохранены как история исследования, но **не доказывают лимиты или тарифы OpenAI upstream**, о котором сообщил пользователь (§3.6). «$100/5h» по-прежнему неизвестно. Proxy назван пользователем; тарифы proxy/provider и usage accounting остаются неизвестными. Аналогия с ассистентской сессией допустима только как источник гипотез, не как доказательство равенства deployment.

**Формула-кандидат, не утверждённый расчёт:** `Σ (токены категории × ставка реально обслужившей модели/категории)`. Для запроса с подтверждённым OpenAI upstream API equivalent определять по фактической модели и применимым тарифам OpenAI с датой/версией цен, а не слепо по Claude model alias или `total_cost_usd` harness. Заявление пользователя не заменяет request-level проверку: публичное описание допускает смешанные upstream (§3.7); для другого provider нужен его применимый прайс. Четыре категории harness (uncached input, output, cache creation, cache read), TTL и семантику кеша необходимо сопоставить с доступными категориями OpenAI; переносимость категорий и ставок не установлена. До сверки раздельно показывать **upstream usage**, **proxy cost** и **harness estimate**: ни одна из этих величин автоматически не равна другой или фактической оплате. Детальные события и result-агрегаты нельзя складывать как независимые расходы: требуется определить источник истины и исключить двойной счёт. Наличие всех нужных полей в runtime проекта пока не подтверждено.

**Эксперимент-кандидат — не выполнен:** начать с офлайн-сверки одного уже существующего обезличенного request id: связать alias запроса, реально обслужившую OpenAI-модель, upstream usage, proxy cost и harness estimate, зафиксировать источник и семантику каждого поля. Без новых платных запусков, публикации логов или секретов; доступность пригодной записи и сквозной привязки пока неизвестна. Затем при наличии данных сверить обезличенный записанный интервал usage с итогом CLI/proxy; проверить resume, retries, subagents, дубли и пропуски. Одиночный request id сам по себе не подтверждает полноту интервального учёта.

### 3.7. Дополнение от 2026-11-12: результат отдельного proxy-исследования

**Источник — переданный координатором результат другого исследователя; автор дополнения внешние источники повторно не открывал, runtime не проверял.**

- Публичная главная [Brotherhood](https://cliproxy.ekb.zozo.gg/) описывает схему **LiteLLM → CLIProxyAPI**: LiteLLM отвечает за ключи, лимиты и расход, CLIProxyAPI — за маршрутизацию. Версии и deployment config не проверены. Claude aliases могут вести на GPT; главная также описывает смешанные тиры Claude/Kimi. Поэтому заявление пользователя об OpenAI upstream (§3.6) нельзя обобщать на **все** вызовы без request-level фактически обслужившей модели.
- В upstream `main` [CLIProxyAPI translator](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/translator/codex/claude/codex_claude_response.go) `input_tokens_details.cached_tokens` переводится в `cache_read_input_tokens`, а cache вычитается из `input_tokens`. Это свидетельство возможной адаптации категорий, не подтверждение поведения установленной версии: deployed version неизвестна.
- [LiteLLM model cost map](https://docs.litellm.ai/docs/proxy/model_cost_map) описывает расчёт token-category × price. Overrides цен и правила usage accounting конкретного шлюза неизвестны.
- [SDK message parser](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/message_parser.py) лишь читает готовое `total_cost_usd` harness; совпадение этого поля с LiteLLM spend не установлено. Наличие SDK-поля не подтверждает источник цен или корректность пересчёта через alias.
- Ни 5h, ни `$100/5h` не подтверждены. Страница OpenAI вернула исследователю 403; конкретное название модели и URL непроверенного поискового результата здесь не фиксируются как факт. Реальные расходы подписки и остаток 5h из найденного не следуют.

**Рекомендация-кандидат, не согласованное решение:** LiteLLM spend — первичный кандидат для учёта расхода шлюза; usage + фактическая upstream model + версия применимого прайса — основа независимой API-equivalent сверки. Для запроса, подтверждённо обслуженного OpenAI, применять тарифы OpenAI (§3.3); для иных upstream сначала установить provider и его тариф. Harness cost оставить диагностикой до сверки. Upstream usage, proxy cost и harness estimate по-прежнему разделены; LiteLLM spend сам по себе не доказывает фактическую оплату подписки.

**Открытый вопрос:** доступен ли пользователю read-only расход/usage в кабинете Brotherhood или обезличенный экспорт? При наличии пригодных данных начать с одного существующего обезличенного request id по §3.3, без новых платных запусков и публикации логов; отдельно установить версии translator, прайса и overrides.

### 8.2. Cumulative/delta, resume, subagents и retries

Текущая [документация cost tracking](https://platform.claude.com/docs/en/agent-sdk/cost-tracking), разделы **Track costs in streaming input mode**, **Accumulate costs across multiple calls**, **Track per-step usage**, устанавливает разные области учёта:

- `result.usage` в streaming input — **текущий turn, только main loop**, без subagents. Его нельзя считать целым деревом работы.
- `total_cost_usd` и `modelUsage/model_usage` — **running totals**, включая subagents и восстановленный spend при resume. Не складывать результаты одной сессии как независимые расходы. Независимые вызовы без resume отличаются от продолжений.
- `/clear`, `/reset`, `/new` сбрасывают running totals; нужна явная граница сегмента, а не правило «всегда взять максимум». После crash/неполного завершения полнота восстановленного baseline требует проверки.
- Для attribution к Run использовать разность проверенных соседних cumulative snapshots **одного сегмента**. Если baseline отсутствует, исторический session total можно назвать snapshot, но нельзя целиком приписывать текущему Run. Отрицательная разность — discontinuity/unknown, не ноль.
- Assistant-сообщения параллельных tools могут иметь один message ID и одинаковый usage: дедупликация обязательна. Документация предупреждает, что per-step `output_tokens` — placeholder; output читать из подходящего result-агрегата. Суммировать assistant usage с result нельзя.
- Retry с новым реальным upstream response ID может быть отдельным расходом; replay одной записи — нет. Успех/ошибка Run сами по себе не устанавливают расход попытки. Без response IDs и полных usage metadata невозможно доказать, что все оплачиваемые retries учтены.

Это документированная семантика текущего harness, **не выполненный runtime-тест 2.1.280**. Статический путь проекта действительно передаёт `resume` (`runner/src/ctrunner/main.py:271–282`); существование transcript проверяется в `main.py:131–136`. Поэтому сумма `Run.cost_usd` имеет конкретный риск повторного включения прежнего spend, а четыре поля `usage.reported` — риск пропуска subagents. Масштаб и наличие проблемы на реальных данных не измерены.

### 8.4. Детерминированный API equivalent — спецификация расчёта, не реализация

Первичный вариант — **upstream usage на уникальный response/attempt**, подтверждённые provider + фактическая модель/revision и зафиксированный прайс. Запись прайса: URL, дата получения/действия, snapshot/hash, валюта, единица (например, за 1M токенов), service tier, context tier и modality; прочие условия, влияющие на ставку. Не угадывать revision по Claude alias или `canonicalModel` pricing lookup.

Для подтверждённой OpenAI-модели с однородными текстовыми категориями:

`E = ((I − C − W) × p_input + C × p_cached + Σ(W_ttl × p_write_ttl) + O × p_output) / 1_000_000 + F_known`

- `I` — исходный полный OpenAI input; `C` — cache read; `W = Σ W_ttl` — отдельная cache-write категория **только если применимый прайс действительно разделяет её**. Если write не выделяется в прайсе, соответствующие токены остаются обычным input, а не вычитаются без начисления. При отсутствии write-категории формула упрощается до `(I−C)×p_input + C×p_cached + O×p_output`.
- `O` уже включает reasoning breakdown: **не прибавлять reasoning к output**. Если тариф делит output на разные категории, сначала построить непересекающееся разбиение по этому тарифу. Для audio/image и иных модальностей текстовой формулы недостаточно.
- При подтверждённой версии translator input из Anthropic-ответа — уже `U=I−C−W`; тогда считать `U×p_input + C×p_cached + Σ(W_ttl×p_write_ttl)`, а не вычитать cache из `U` ещё раз. При неподтверждённой семантике cache — unknown, не автоматическая нормализация.
- `F_known` — только подтверждённые тарифицируемые нетокенные услуги; не выдумывать плату за tool calls. Нулевые cache/write разрешены только при документированной семантике отсутствующего поля или явном 0.
- Проверять неотрицательные целые counters, `C+W≤I`, необходимые разбиения и единицы; считать decimal без промежуточного округления, округлять итог по зафиксированному правилу. Противоречие/нет модели/прайса/нужного TTL → `unknown` с причиной. Можно показать известный subtotal + число unknown-записей, но не назвать это полным расходом.
- `model_usage` — запасной источник per-model cumulative counters, а не per-request upstream ledger. При доказанных модели, границах и стабильном тарифе возможен **aggregate estimate** по разностям; при context/service-tier сменах агрегата недостаточно. Его `costUSD` остаётся harness estimate, не входной ценой для независимой сверки.
