# PR36: свежая диагностика за полным окном при drain

## Проблема и доказательство

Статическое замечание воспроизведено live WebSocket-тестом: старый совместимый получатель рекламирует только `harness_diagnostic_v1`, оставляет историческую диагностику без ACK. После заполнения окна 256 отправляется drain, а в журнал добавлен последний result за 520 старыми источниками. До исправления оба варианта (с ACK свежего результата и без ACK) упали: отправлены только первые 256 исторических diagnostics, свежая не прочитана. RED: **2 failed**.

## Минимальное исправление

`runner/src/ctrunner/gateway.py::_diagnostic_loop`:
- при начале drain старые pending получают последнюю возможность ACK в течение 50 мс;
- пока есть непрочитанный хвост журнала, истёкшие leases освобождают ограниченное окно без записи receipt;
- новые окна в drain получают такую же короткую lease, позволяя дойти до свежего хвоста;
- при достижении EOF последнее окно сохраняется для ожидания ACK до общего deadline;
- повторного циклического прохода при drain нет; прежний общий бюджет 4 секунды, внешний shutdown-бюджет 5 секунд не увеличены.

Legacy payload, source IDs, public ACK/cursor и canonical conflicts не меняются. Отсутствие ACK не превращается в принятие либо окончательный отказ. Отложенные источники остаются в retained journal и повторяются при новом подключении.

## Ограничения

Доставка при отказе сети или ACK за пределами deadline не гарантируется. Источники, вытесненные из горячего окна, могут ожидать следующего подключения; восстановление зависит от сохранности журнала. Не обещается прочитать произвольно большой журнал за 4 секунды. Размер pending остаётся ограничен 256.
