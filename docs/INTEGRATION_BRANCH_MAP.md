# Карта веток и интеграции CoreTeams

Статус документа: рабочая карта для ревью и управляемого слияния.  
Срез GitHub: 30 октября 2026 года.  
Целевая ветка слияния: `release/coreteams-integration-2026-10-27`.

## Правило интеграции

`master` — текущая продуктовая ветка, но не место для прямого включения незавершённых компонентных работ. Все изменения сначала собираются и проверяются в `release/coreteams-integration-2026-10-27`. Деплой не является следствием merge сам по себе: источник публичного стенда ведётся отдельно.

Порядок включения в ветку слияния:

1. Storage-изоляция: PR #13.
2. Целостность сохранения артефактов: PR #14.
3. Мост React B — gateway: PR #15.
4. Пакет проверки и развёртывания: PR #16.
5. React Prototype B: PR #11.
6. Совместная проверка `web + gateway + runner + storage` и только затем отдельное решение о переносе в `master` и публикации на стенд.

PR не становится готовым к слиянию только из-за указанного порядка: требуются ревью, актуальная база, разрешённые конфликты и проверки по договорённостям компонента.

## Конфликты и точки сверки

### PR #15: React B — gateway

GitHub сообщает `mergeable: false` для PR #15. Ветка `demo-gateway` ушла от общего предка на четыре коммита, а ветка PR #15 — на два. Изменения пересекаются в следующих границах:

- `backend/main.py` — подключение маршрутов и API;
- `backend/models.py`, `backend/schemas.py` — модели и контракты;
- `backend/public_events.py` — события для клиента;
- `backend/repository.py` — сохранение и чтение состояния;
- `backend/runner_executor.py` — запуск runner;
- `backend/tests/test_repository.py` — совместимость поведения.

Это контрактный конфликт, а не конфликт форматирования. Разрешение должно сохранить единый маршрут API, модели данных, формат публичных событий, связь Run/Project и поведение runner. Точные конфликтные hunks фиксируются отдельным пробным переносом на ветку слияния; этот документ их не выдумывает.
