
# 2.4. Запуск Claude Code в контейнере

**Владелец:** Илья. **Поддержка:** Филипп по инфраструктуре и сети. **Демо:** 28 сентября. **Связано с:** 2.2 (инфраструктура), 2.3 (данные), 2.1 (вывод сессии).

## 1. Намерение

Сессия агента запускается в изолированной среде с данными конкретного клиента, продолжает работу после закрытия браузера и восстанавливается после перезапуска. Заказчик получает доказательство, что фоновая работа возможна.

Критерий намерения: человек закрывает браузер, возвращается через час и видит, что работа продвинулась.

## 2. Что должно работать (поведение)

- Контейнер стартует с данными проекта клиента.
- Сессия регистрируется в гейтвее и видна снаружи.
- Проверка живости отличает три состояния: работает, зависла, упала.
- Перезапуск контейнера не теряет подтверждённую работу.
- Сессия не видит данные других проектов.
- Работа продолжается, пока браузер закрыт.

## 3. Контракты

Реализация — пакет `runner/` (`ctrunner`), дизайн — `docs/plans/2026-09-25-runner-design.md`.

### Образ

`coreteams-runner:<ver>`, собирается из `runner/Dockerfile`.

| Что | Значение |
|---|---|
| База | `python:3.12-slim` |
| Claude Code | внутри `claude-agent-sdk==0.2.158` (бинарник в пакете, Node.js не нужен) |
| CTF | `noxxer/core-team` @ `416507a` (5.5.0), шаблон в `/opt/ctf/.claude` |
| Утилиты | `git jq gawk diffutils curl procps ca-certificates` |
| Зависимости Python | строго по `uv.lock`, `pip install --require-hashes` |
| Пользователь | `agent` (uid 1000), root в рантайме не используется |
| Размер | 554 MiB (замер 2026-09-25) |
| Потребление (замеры песочницы) | RAM 181–279 MiB, CPU ~3–4 % ядра на сессию |
| Лимиты запуска | `--memory 1g --cpus 1 --pids-limit 256` |
| Жёсткость | `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--init` |
| Перезапуск | `--restart on-failure:5`; exit 78 (ошибка конфигурации) повторами не лечится |
| HEALTHCHECK | `ctrunner-healthcheck`, интервал 15 с, 2 попытки, старт 60 с |

### Монтирование

| Путь в контейнере | Источник | Права | Назначение |
|---|---|---|---|
| `/workspace` | том `proj-<id>` | rw | единственное постоянное хранилище проекта |
| `/workspace/project` | — | rw, cwd агента | git-репозиторий проекта с `.claude/` (CTF) |
| `/workspace/.runner` | — | rw, агенту закрыт сторожем | `events.jsonl`, `inbox/` |
| `/workspace/claude` | — | rw, агенту закрыт сторожем | `CLAUDE_CONFIG_DIR`: транскрипты для resume |
| `/seed` | каталог данных проекта (от 2.3) | ro | копируется в `project/` при первом старте |
| `/run/secrets` | `~/.config/coreteams/secrets/<id>` | ro | ключ cliproxy |
| `/tmp` | tmpfs | rw | временные файлы агента |
| `/home/agent` | tmpfs (uid 1000) | rw | `HOME` при read-only rootfs |
| `/run/ctrunner` | tmpfs (uid 1000) | rw, вне корней сторожа | `health.json`: агент не может подделать свой статус |
| остальное | образ | ro (`--read-only`) | — |

Других проектов в контейнере физически нет: смонтирован только свой том.
Сторож PreToolUse разрешает инструментам только `/workspace/project` и `/tmp`
(Bash дополнительно — `/usr`, `/bin`, `/lib`, `/dev/null`); для Bash это эвристика, граница — монтирование.

### Секреты

- Передача: файл `/run/secrets/anthropic_token` (bind mount, ro). В env, образ и `docker inspect` ключ не попадает.
  `sessions secrets init <id>` пишет файл из окружения шлюза (каталог 0700, файл 0600).
- Fail-fast: нет файла, пустой, короче 8 символов или с пробелами → exit 78 до старта SDK.
  Ключ проверяется запросом к cliproxy: 401/403 → exit 78; сеть недоступна → exit 1, Docker перезапустит.
- Redact: значение ключа вырезается (`***`) из журнала событий и stderr SDK.
- Отзыв: ключ свой на каждый проект; отозвать его в cliproxy, затем `sessions secrets init <id>` с новым ключом и `sessions restart <id>`.
- Известный риск: агент работает под тем же пользователем и через Bash может прочитать ключ из окружения CLI.
  Смягчение — отдельный отзываемый ключ на проект; вынос ключа из контейнера (sidecar) — следующий шаг.

### Регистрация в гейтвее

Контракт — `docs/2.4/protocol.md`: runner сам подключается к гейтвею по WebSocket (у контейнера 0 входящих портов),
первым сообщением отправляет `hello{project_id, runner_version, session_id, last_seq}`, затем heartbeat каждые 10 с и события.

Этап 1 (демо 28.09): гейтвея нет. Сессия видна через локальный журнал `/workspace/.runner/events.jsonl`
(`sessions logs <id>`), статус — через `sessions status <id>`, команды — через файловый inbox (`sessions send`).
Формат событий журнала совпадает с `event` протокола.

### Правило проверки живости

Runner хранит фазу хода и время последнего прогресса. Прогресс — любое сообщение SDK, включая потоковые токены,
вызов хука PreToolUse, запрос разрешения на инструмент, начало хода.

| Фаза (`phase`) | Условие | Здоровье (`health`) |
|---|---|---|
| `idle` — хода нет | любое | `ok` |
| `awaiting_answer` — развилка ждёт человека | любое | `ok` (человек думает — не зависание) |
| `working` | прогресс был не дольше `T` назад | `ok` |
| `working` | прогресса нет дольше `T` | `stalled` |
| `failed` — SDK упал или диск полон | — | `crashed`, процесс выходит с кодом 1 |
| любая | heartbeat не обновлялся дольше 30 с | `crashed` (так считает гейтвей и HEALTHCHECK) |

`T = STALL_AFTER_S = 720 с`: максимальный таймаут Bash в Claude Code — 10 мин, плюс 2 мин запаса на ответ модели.
Runner пишет `/run/ctrunner/health.json` каждые 10 с; `ctrunner-healthcheck` возвращает 0 только при `health = ok`
и свежем файле, поэтому `docker ps` показывает `unhealthy` и без гейтвея. Зависшую сессию runner не убивает — решает человек.

## 4. Критерии приёмки

1. Сессия стартует с данными проекта и выдаёт результат.
2. Гейтвей видит запущенную сессию.
3. Зависшая сессия определяется как зависшая, а не как работающая.
4. После перезапуска контейнера работа продолжается.
5. Попытка доступа к данным другого проекта отклоняется и попадает в журнал.

## 5. Негативные сценарии и границы

- Контейнер падает на середине работы.
- Закончилось место на диске.
- Секрет недоступен — сессия не должна стартовать «наполовину».
- Сессия пытается выйти за пределы своей рабочей директории.
- Долгая работа без событий: как отличить паузу от зависания.

## 6. Что вне границ

Много одновременных сессий, автомасштабирование, несколько узлов, оптимизация расходов на простой.

## 7. Eval-проверки

- Автоматически: запуск сессии с тестовым проектом и проверка события «началась работа».
- Автоматически: перезапуск контейнера и проверка, что проект продолжается.
- Вручную: проверка изоляции — попытка прочитать каталог другого проекта.
- Вручную: имитация зависания и проверка определения состояния.

## 9. Риски и допущения

- **Скрытое состояние внутри процесса** — минус варианта с постоянной средой, который заказчик советовал проверить первым. Если состояние непрозрачно, восстановление будет ненадёжным.
- Требования к ресурсам могут оказаться выше ожидаемых.
- Проверка живости легко превращается в формальность, если не определить признак зависания заранее.

## 11. Как проверяем AI-часть

**AI-части нет.** Направление детерминированное: результат либо работает, либо нет. Проверка — обычные критерии приёмки из раздела 4. Если модель здесь появится позже, раздел заполняется по файлу «Блок — как проверяем AI-часть».
