# Пакет результата (ZIP) и его валидатор

Задача PPS-138. Источники: skill `coreteams-pilot-result` и `handoff/2026-10-15/pilot-package.md` (репозиторий `pokatyusha/project-harness`), `web-app/docs/pilot-result-contract.md` (ветка `codex/coreteams-react-handoff-2026-10-15`), `web-product/docs/ctf-v2-contract.md` (ветка `codex/coreteams-v92-product-workspace-2026-10-15`; контракт **proposed**, не принят). Код — `runner/src/ctrunner/result_package.py`, тесты — `runner/tests/test_result_package.py`.

Валидатор проверяет **форму** пакета. Он не доказывает, что источники существуют и подтверждают написанное, что выводы верны, что согласие участника получено, что эксперт проверял результат и что результат полезен. «ok» значит «структура допустима», не «результату можно доверять».

## Формат

Имя: `coreteams_<project-id>_<task-id>_<run-id>_<phase>_<build-version>.zip`; идентификаторы — `[A-Za-z0-9.-]+` (подчёркивание зарезервировано разделителем), `phase` — `baseline` | `prototype`. В корне ровно четыре файла, без каталогов:

| Файл | Содержание |
|---|---|
| `result.md` | девять разделов `##` в порядке: Decision requested, Short answer, What the evidence says, Comparison or reasoning, Unknowns and limitations, Recommended next step, Expert review / escalation, Contributions, Sources |
| `sources.csv` | столбцы по порядку: `source_id,title,publisher,author,published_at,accessed_at,url,claim_ids,source_type,limitations` |
| `metadata.json` | `project_id, task_id, run_id, phase, build_version, environment, created_at` (с часовым поясом), `operator_id, input_scope, consent_status, result_schema_version, limitations`; при участнике — `participant_id` (псевдоним) и `consent_text_version` |
| `manifest.json` | `{"files": [{filename, media_type, byte_size, sha256, schema_version}, ...]}` — три payload-файла; сам manifest не перечисляется (самохэш невозможен); хэш — от байтов в архиве |

Media type: `text/markdown`, `text/csv`, `application/json` (допустим суффикс `; charset=utf-8`). Все файлы — UTF-8 без BOM.

## Что проверяется

Результат — `Report(violations, source_count, not_verified)`; ожидаемые нарушения возвращаются значениями, а не исключениями. Каждое нарушение — `Code` (закрытый `StrEnum`), файл и пояснение без значений из пакета (найденный e-mail или токен в отчёт не попадает, только вид и номер строки).

1. **Контейнер** (при нарушении содержимое не распаковывается и не разбирается): это ZIP; размер ≤ 10 МиБ; ≤ 16 записей; нет абсолютных путей, `..`, `.`, обратных слэшей, `:`, NUL; нет симлинков, каталогов и устройств; нет шифрования; нет повторяющихся имён; набор файлов ровно четыре; член ≤ 5 МиБ и суммарно ≤ 10 МиБ — и по заголовку, и по фактически прочитанному (чтение с потолком, заголовку не верим); степень сжатия ≤ 100:1 для членов крупнее 64 КиБ; CRC/распаковка целы.
2. **Кодировка и JSON**: строгий UTF-8, без BOM, не пусто; JSON — объект без повторяющихся ключей и `NaN`/`Infinity`.
3. **metadata**: все обязательные поля, неизвестные запрещены (поля с именами `email/phone/contact/password/secret/token/...` — как приватные данные), ID по шаблону, `phase`, `created_at` — ISO 8601 с поясом, `limitations` — непустая строка или список строк; имя ZIP совпадает с metadata (если имя передано).
4. **manifest**: единственный ключ `files`; у записи ровно пять ключей; ровно три payload по одному разу, `manifest.json` в списке запрещён; `media_type`; непустой `schema_version`; `byte_size` и `sha256` (64 hex, нижний регистр) равны фактическим.
5. **sources.csv**: заголовок точно как в контракте; длина строк; уникальные `source_id` вида `S<число>`; непустые `title, accessed_at, url, claim_ids, source_type, limitations`; `url` — прямой публичный http(s) без логина/пароля, не localhost и не частный IP; даты — ISO 8601. Пустая таблица (только заголовок) допустима лишь при явной фразе «insufficient evidence» / «недостаточно данных|доказательств|источников» **и** в Short answer, **и** в `metadata.limitations`.
6. **result.md**: все девять разделов, по одному разу, в порядке контракта, непустые; «Not applicable» без причины не принимается; заголовки внутри блоков кода не считаются; допускается нумерация и выделение (`## 2. **Short answer**:`). Ссылки `[S<n>]` вне раздела Sources должны существовать в `sources.csv`; каждый источник из CSV процитирован и перечислен в Sources; перечисленное в Sources есть в CSV; при непустых источниках в «What the evidence says» есть ссылки.
7. **Приватные данные** (все четыре файла): e-mail, телефон, локальные пути (`/home/`, `/Users/`, `/root/`, `/tmp/`, `/var/`, `/run/`, `/workspace/`, `~/`, `C:\Users\`), секреты (`sk-…`, `ghp_…`, AWS/Google/Slack-ключи, JWT, `Bearer …`, `token=…`, приватные ключи), учётные данные и секретные параметры в URL. Пути и телефоны в URL игнорируются.
8. **Роли ИИ**: Contributions обязан назвать роли ИИ/автоматическим анализом (`AI`, `ИИ`, `automated`, «автоматический»…); в нём нельзя имя человека (инициалы, отчество, `Dr./Prof.`, `д-р`, `@handle`); в Contributions и Expert review нельзя заявлять проверку человеком («reviewed by a …», «проверено юристом…») без отрицания — подтверждающего поля в metadata нет.

## Чего не проверяется

Это же возвращается в `Report.not_verified`.

- Существование источников, доступность URL, соответствие источника утверждению, его авторитетность. Сеть не используется.
- Истинность выводов; то, что **каждое** фактическое утверждение снабжено ссылкой (видны лишь ссылки вида `[S1]`).
- Фактическое согласие участника (проверяется только наличие `consent_status` и версии текста), допустимость самих значений `consent_status`.
- Фактическую проверку специалистом, полезность результата, пригодность для решения.
- Персональные данные вне шаблонов (имена, адреса, нестандартные токены). Проверки имён людей, заявлений о проверке и фразы «недостаточно данных» — эвристики, обходятся перефразировкой.
- Метки типа свидетельства (факт / самоотчёт / допущение / контрфактическое…) в `result.md`.
- Совпадение содержимого с исходными материалами участника; отсутствие недопущенных документов — только по набору файлов.

## Запуск

```bash
cd runner
uv run ctrunner-result-package validate path/to/coreteams_<...>.zip   # JSON-отчёт; код 0 — структура допустима, 1 — есть нарушения, 64 — неверный вызов
uv run ctrunner-result-package path/to/coreteams_<...>.zip            # то же без подкоманды (обратная совместимость)
```

Из кода: `validate_file(Path)` (передаёт имя файла и сверяет его с metadata), `validate_bytes(raw, filename=None)` — чистое ядро без ввода-вывода (без имени сверка с metadata пропускается и отмечается в `not_verified`), `validate(bytes | Path)`. Прогон не имеет побочных эффектов, ничего не распаковывает на диск.

## Сборка

Код — `runner/src/ctrunner/result_package_build.py`, тесты — `runner/tests/test_result_package_build.py`. Модель пишет `result.md`, `sources.csv`, `metadata.json`; `manifest.json` и ZIP строит детерминированный код, затем сразу прогоняет получившийся архив через валидатор. Шаблон инструкции для модели — [`result-package-prompt.md`](result-package-prompt.md).

```bash
cd runner
uv run ctrunner-result-package build ./brief/ ./out/            # каталог с тремя файлами -> ./out/coreteams_<...>.zip
uv run ctrunner-result-package build ./brief/ ./out/ --overwrite --created-at 2026-10-15T12:00:00+03:00
```

Коды выхода: `0` — архив собран, прошёл валидацию и записан (в stdout JSON-отчёт с `filename` и `path`); `1` — отказ сборки (в stdout отчёт с нарушениями, файл **не** записан) либо ошибка ввода-вывода или существующий файл без `--overwrite` (причина в stderr: тип ошибки, без содержимого); `64` — неверный вызов.

Из кода: `build_package(result_md, sources_csv, metadata, *, created_at) -> Built | Rejected` — чистое ядро; `build_from_dir(src, out, *, overwrite=False, created_at=None) -> Written | Rejected` — оболочка.

Что делает сборщик:

- **manifest.json** строится по реальным байтам: `byte_size`, `sha256`, `media_type`; `schema_version` каждого файла — константа `MANIFEST_SCHEMA_VERSION = "1"` (контракт не связывает её с `result_schema_version`). Сам manifest в списке не перечисляется.
- **created_at** — аргумент сборки (`--created-at`; по умолчанию значение из `metadata.json`, а при его отсутствии или порче — текущее UTC), обязательно с часовым поясом; он записывается в `metadata.json` поверх присланного. Остальные поля metadata не меняются и не придумываются.
- **Имя ZIP** берётся из metadata (`project_id, task_id, run_id, phase, build_version`), поэтому с ней согласовано. Если эти поля не годятся для имени, архив всё равно проверяется (без сверки имени), и отказ несёт нарушение `metadata_schema`.
- **Детерминизм**: порядок `result.md, sources.csv, metadata.json, manifest.json`; даты записей `1980-01-01 00:00:00`; без extra-полей и комментариев; атрибуты `0644`, `create_system=3`; сжатия **нет** (`ZIP_STORED`): байты DEFLATE зависят от версии zlib. JSON сериализуется с отсортированными ключами, `ensure_ascii=False`, отступ 2, перевод строки в конце. Одинаковые входы и `created_at` дают побайтово один и тот же архив.
- **Отказ**: если валидатор находит нарушения, `Rejected` несёт `Report` с теми же `Code`, что и `validate_*`; ничего не записывается. Принятый архив — всегда тот, что прошёл `validate_bytes(data, filename)`.
- **Чтение каталога**: источники открываются без следования симлинкам (`O_NOFOLLOW`, включая сам каталог), только обычные файлы (FIFO и устройства отвергаются), не больше 5 МиБ + 1 байт на файл. Недоступный файл — нарушение `unreadable`.
- **Запись**: временный файл в каталоге вывода -> `fsync` -> `link` без перезаписи (при существующем файле — `FileExistsError`, чужой файл не тронут) либо `replace` при `--overwrite`; временный файл удаляется в любом случае. Каталог вывода должен существовать.
- Содержимое файлов не логируется и не печатается; в отчёте — только коды, файлы и пояснения без значений.

**Сборщик не доказывает истинность источников.** Успешная сборка значит «структура допустима» в том же смысле, что и `ok` валидатора: он не проверяет, что источники существуют и подтверждают утверждения, что выводы верны, что согласие и экспертная проверка были, и не исправляет содержимое — упаковывает допустимое либо отказывает. `Report.not_verified` возвращается и при успешной сборке.

## Неоднозначности контракта и принятое прочтение

Везде выбрано самое строгое прочтение; если реальный экспортёр с ним не согласен, менять нужно константы в начале модуля.

1. **Имена разделов** — английские, как в контракте; локализованные заголовки не принимаются. Для русских заголовков нужна таблица синонимов.
2. **Порядок разделов** считается обязательным («readable order» в skill).
3. **Список «Sources» в result.md** должен содержать все ID из CSV (контракт требует лишь согласованности).
4. **`source_id`** — `S<число>` (в контракте «stable ID», пример `[S1]`).
5. **Обязательные столбцы sources.csv**: `source_id, title, accessed_at, url, claim_ids, source_type, limitations`; `publisher`, `author`, `published_at` могут быть пустыми («if available»). `limitations` обязателен у каждой строки («limitations recorded»).
6. **Тип `limitations` в metadata** не определён: принимаются строка и список строк.
7. **Значения `consent_status`** не перечислены; проверяется только непустота. Участник → обязателен `consent_text_version`.
8. **Лишние ключи** в metadata и в корне manifest запрещены (контракт перечисляет поля, но не говорит «только они»). Это ломает расширение схемы без правки валидатора.
9. **`schema_version` в manifest** — непустая строка; равенство `metadata.result_schema_version` не требуется (в контракте не связаны).
10. **Media type** фиксирован; контракт его значений не называет.
11. **Явное «insufficient evidence»** контракт требует «в теле и в metadata», но формулировку не задаёт; принят список фраз (en/ru) и требование к Short answer.
12. **BOM** в CSV/JSON/Markdown запрещён (Excel добавляет BOM — экспорт из Excel не пройдёт).
13. **Версия ctf-v2-contract** не описывает содержимое ZIP, лишь отсылает к skill; отдельного формата нет.
14. **Лимиты** (10 МиБ, 5 МиБ на файл, 100:1) в контракте не заданы — выбраны консервативно.

## Как адаптировать skill к runner / CTF

Только описание; ничего не регистрируется в продакшн-конфигурации. Skill `coreteams-pilot-result` пишет и проверяет пакет в одном месте, runner разделяет эти роли:

1. **Промпт/skill роли-автора**: положить в системный промпт роли-финализатора (или в skill, подключаемый к её сессии) разделы 1–3 skill: девять заголовков `##` ровно как в таблице выше; правила `[S<n>]` и «нет источника — нет утверждения»; запрет контактов, путей и секретов; формулировка Contributions («роли — ИИ, не люди; человеческая проверка не проводилась»); при нехватке данных — явное «Insufficient evidence» в Short answer и в `limitations`.
2. **Что передавать роли**: `project_id/task_id/run_id/phase/build_version/environment/operator_id` и псевдоним участника с `consent_text_version` — из заявки на Run, а не из диалога; `created_at` ставить в момент упаковки, с поясом. Источники роль заводит только из реально открытых страниц (URL, дата доступа, ограничения).
3. **Упаковка вне модели**: `result.md`, `sources.csv`, `metadata.json` пишет роль; `manifest.json` и ZIP строит детерминированный код (хэши от точных байтов), а не LLM — см. «Сборка».
4. **Проверка**: после упаковки вызвать `validate_file` и не отдавать архив gateway/хранилищу, пока `report.ok` ложно; нарушения вернуть роли для исправления (в отчёте нет приватных значений, их можно показывать). Артефакт ZIP gateway отдаёт только для сохранённой неизменяемой версии (`ctf-v2-contract`).
5. **Отдельно от валидатора**: человеческая или отдельная ИИ-проверка источников и выводов (существуют ли URL, подтверждают ли утверждения), согласие участника и экспертная эскалация. Структурный `ok` не заменяет ни одну из них.
6. Не включать пользовательские файлы и сырые ответы в ZIP без явного разрешения на конкретное включение; валидатор по набору файлов этого не допускает.
