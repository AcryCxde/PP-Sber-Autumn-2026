# Админка CoreTeams: целевой дизайн

**Дата:** 2026-11-12. **Статус: APPROVED — одобрено пользователем 2026-11-12 («Утверждаем»).**
Это дизайн, не план реализации. Код, запуск приложения и платные вызовы не выполнялись.
Источник согласований и прежних доказательств: `docs/research/2026-11-12-admin-redesign.md`, особенно §6.
Пользователь одобрил дизайн целиком после согласования оценки харнесса; формулировки «предлагается» ниже сохраняют историю выбора технических defaults, теперь входящих в одобрение.

## 1. Цель, границы и решения

Единый сайт с общей оболочкой; администратор видит текущую работу, разбирает проблемы и управляет AI-доступом.
Согласованы три блока обзора, отдельная страница Users и AI-only заморозка без срока до ручного снятия.
Согласовано: текущая работа завершается; новые AI-запуски запрещены; причина доступна только администраторам.
Не входят: полный бан, блокировка входа, отзыв auth-сессий, денежные лимиты, фактический биллинг и сверка Brotherhood.
История: после §8.7 журнала было отдельно согласовано только название/источник «Оценка расхода по харнессу, USD»; последующее «Утверждаем» одобрило весь дизайн.
Это корректирует прежний полный отказ от денежных показателей; не добавляем общий денежный KPI до надёжной attribution.
Не добавляем новые WebSocket, декоративные charts и admin retry/cancel.
Техническое завершение не означает одобрение результата или достижение цели пользователя.

## 2. Архитектурный выбор — предложение

**Рекомендуется A: перенести админку в основной frontend Shell.**
Две страницы: `Overview` («Обзор») и `Users` («Пользователи»); предлагаемые маршруты `#admin/overview`, `#admin/users`.
Один header, навигация, переключатель темы и меню аккаунта; без второй шапки и ссылки «Интерфейс CoreTeams».
Админская навигация видна по роли, но все данные и действия независимо защищены серверным `AdminUser`.

| Вариант | Когда разумен | Цена / ограничение |
| --- | --- | --- |
| A. Админка внутри Shell | Нужен единый сайт, admin — часть основного продукта | Перенос компонентов и маршрутов; зато одна оболочка и меньше точек расхождения |
| B. Две сборки с одинаковым видом | Важна независимость выпуска текущего product UI | Меньше переноса сейчас, но дублирование header/theme/account и сохранение перехода между приложениями |
| C. Shared shell для двух сборок | Обе сборки должны жить независимо долго | Реальное переиспользование, но общий пакет, контракт и координация выпусков сложнее задачи двух страниц |

A непосредственно решает пользовательскую проблему без новой инфраструктуры shared shell.
Перенос касается админки, не всего `web-product`; судьба остальных страниц второй сборки вне этого дизайна.
Старый `/product/#admin` после переключения направляет в новый Overview, без параллельных интерфейсов управления.

## 3. Данные и термины: проверенные границы

Узкая статическая проверка дополняет журнал; поведение production не проверено.
`backend/models.py:140–174`: Run имеет id, status, started_at, completed_at, error_code; собственного stage нет.
`backend/models.py:403–428`: ProjectRun связывает Run с проектом, stage, kind и product_run_id; accepted хранится отдельно.
`backend/product.py:279–328`: продуктовый статус может быть waiting_for_input после completed; это не running Run.
`frontend/src/coreteams/router.ts:4–29`: существуют маршруты проекта/workspace, отдельного admin run detail нет.
`frontend/src/coreteams/Workspace.tsx` содержит версии, этапы и пользовательский повтор; это не admin-диагностика.
Эти выводы — чтение исходников, не аудит, не результат тестов или запуска приложения.

**Предлагаемая единица UI:** «Задача» — человекочитаемый контекст проекта/диалога; «Запуск» — конкретный Run.id.
Одна задача может включать несколько запусков: этап, доработку, ответ/продолжение. Счётчики считают Run, не проекты.
Одна строка оперативного списка = один Run; повторный запуск — другая строка, повтор доставки события — нет.
Этап показывается только по связи конкретного ProjectRun.stage с проверенным каталогом сценария.
Не подменяем исторический этап текущим Project.stage; при недоступной связи: «Этап недоступен».
Не выводим внутренний шаг модели, процент готовности или придуманные стадии по длительности/логам.
Без контекста показываем короткий Run ID; без владельца — «Пользователь не определён», не исключаем запись из итогов.

## 4. Overview: вопрос → действие → данные

Форма — два оперативных списка и строка абсолютных итогов; график не помогает найти конкретный сбой.
У каждого блока отдельная область действия фильтров; период итогов не скрывает старый активный запуск.

| Поле / блок | Вопрос → действие | Источник / ограничение |
| --- | --- | --- |
| Активные: задача + Run ID | Что выполняется? → открыть безопасные детали запуска | Run и доступная связь с проектом/диалогом; не сырой пользовательский промпт |
| Пользователь | Кого затрагивает? → найти его в Users | Conversation.owner_id → User; отсутствие явно обозначено |
| Статус, этап | Выполняется или ожидает старта, в каком контексте? → проверить детали | pending / running; этап только из подтверждённой связи |
| Начало, время с начала | Когда началось? → сопоставить с деталями | started_at → время серверного снимка; без начала «Ещё не начат» |
| Ошибка / неизвестный исход | Что требует разбора? → открыть диагностику | failed и outcome_unknown отдельно, не объединять в «ошибки» |
| Время проблемы, пользователь | Когда и у кого? → найти соответствующий запуск/пользователя | completed_at; при отсутствии «Время исхода недоступно», отдельно начало |
| Итоги периода | Насколько масштабна проблема? → открыть соответствующую выборку Run | Уникальные Run одной когорты; определения ниже |

«Сейчас выполняется»: running; pending виден в том же блоке отдельно как «Ожидает запуска», не как выполнение.
Сортировка: running по started_at от старых к новым, затем pending; отсутствие timestamp не заменяется нулём.
Длительность — контекст, не доказательство зависания; нет автоматического красного порога или ярлыка «зависло».
«Требует внимания»: по умолчанию failed и outcome_unknown за последние 7 суток по started_at, новые проблемы сверху.
Область явно подписана; расширение периода позволяет найти старые проблемы. Это не очередь подтверждённых инцидентов.
Записи без started_at доступны отдельным фильтром «Без времени начала» и не теряются молча.
Нет кнопок «устранено», retry/cancel и обещания автоматического восстановления неизвестного исхода.

### Итоги за период — предлагаемые defaults

По умолчанию последние 7 × 24 часа до серверного момента открытия; доступны 24 часа, 7/30 суток и свой интервал.
Выбранные start/end фиксируются до смены периода или явного «Обновить период», видны в подписи.
Когорта: уникальные Run.id со started_at в полуоткрытом интервале **[start, end)**, без фильтра наличия владельца.
Времена запроса и вычисления — UTC; display — локальная зона браузера с явным обозначением зоны.
При пользовательском интервале локальные границы переводятся в UTC; конец исключён, включая переходы DST.
На одном серверном снимке: N запусков; F failed из N; U outcome_unknown из N; R running из N.
Показывать абсолютные числа и общий знаменатель N, без процентов, трендов и смешения разных когорт.
Итоги исходов отражают текущий status этих Run на момент снимка, не число событий завершения внутри периода.
Completed не равно accepted; одобрение результата не входит в эти метрики. Числа F/U/R не обязаны суммироваться в N.
Pending обычно не имеет started_at и не входит в N; если время есть, входит в N, но не в R.
Отдельная подпись «Без времени начала: K, вне когорты» показывает полноту данных, не привязывая K к периоду.
Нулевые значения разрешены только при успешном полном ответе; неизвестность/неполнота маркируется, не превращается в 0.

### Безопасные детали — предлагаемая read-only панель внутри Overview

Новая admin-панель нужна: существующий workspace не доказывает доступ администратора к чужой задаче.
Поля: Run ID, разрешённые идентификаторы контекста, пользователь, подтверждённый этап, status, timestamps, error_code.
Вместо raw error/log/prompt — серверная allowlist безопасных диагностических полей и нейтральное пояснение кода.
Unknown: «Исход неизвестен; перед повтором требуется проверить сохранённые результаты»; ничего не перезапускать.
Следующее действие: скопировать Run ID для разбора ответственным; при необходимости открыть Users для проверки AI-доступа.
Ссылка на проект — только при существующем праве просмотра; роль admin не даёт неявного доступа к чужому workspace.
Отсутствующие детали обозначаются явно; секреты, содержимое файлов и приватные сообщения в admin-ответ не включаются.

### Диагностическая оценка харнесса — ограниченное согласование

В read-only деталях допустима «Оценка расхода по харнессу, USD» с явным scope конкретной сессии/запуска.
Подпись: «Оценка харнесса; не фактическое списание, не остаток подписки и не проверенный API equivalent upstream».
Scope — безопасное техническое следствие ограничений данных, не отдельное уточнение/одобрение пользователя.
Session total показывается как накопительный snapshot указанной сессии/сегмента на момент наблюдения, не как цена текущего Run.
Delta конкретного Run допустима только по доказанным соседним snapshots одного сегмента с надёжной связью и baseline.
Cumulative snapshots нельзя складывать как независимые Run costs; resets/отрицательная delta/неизвестный scope → unknown, не 0.
При непроверенном resume baseline не показываем полный итог по пользователю/периоду; Run.cost_usd сам по себе недостаточен.
Нет надёжного scope — «Оценка недоступна: область учёта не подтверждена» вместо числа; нет общего денежного KPI/лимитов.
Проверка resume baseline и LiteLLM reconciliation отложены; новые платные эксперименты не требуются и не выполняются.

## 5. Users и AI-заморозка

Предлагаемые минимальные колонки: email, зарегистрирован, последний визит, AI-доступ, действие.
Email → кого менять; registered → различить новый/давний аккаунт; last_seen → понять актуальность контакта.
AI-доступ → разрешены ли новые AI-запуски; действие → заморозить/снять. Неизвестный last_seen = «Нет данных».
Статусы «Разрешён» / «Заморожен», не «Аккаунт заблокирован». Просмотр проектов и вход не запрещаются.
Серверный поиск по email (без учёта регистра), debounce 300 мс; серверная пагинация по 25 записей.
Стабильная сортировка registered DESC + user ID; поиск сбрасывает страницу; нет клиентской загрузки всех пользователей.

Модальное подтверждение заморозки: email, правило завершения текущего запуска, внутренняя причина, подтверждение.
Предлагается обязательная непустая причина до 1000 символов; не просить секреты/персональные подробности.
Снятие — отдельное подтверждение с необязательной внутренней заметкой; без даты автоматического снятия.
Рекомендация минимального аудита: actor ID, серверное время, target ID, action freeze/unfreeze, private reason.
Поля Users, минимальный аудит и технические defaults приняты в составе общего одобрения дизайна 2026-11-12.
Запись политики и аудита атомарна; при ошибке состояние не меняется. Уведомление UI — только после ответа сервера.
При конфликте версии политики — обновить строку и потребовать повторного подтверждения, не перезаписать молча.
Повтор одного подтверждения идемпотентен; disabled-кнопка сама по себе не защищает от повторного запроса.

### Граница AI-доступа — предложение, не описание готовой state machine

Допуск привязан к **конкретному Run**, а не ко всему проекту или бесконечной conversation/session.
Допуск означает окончательное серверное разрешение начать исполнение конкретного Run, атомарно упорядоченное с freeze.
Создание pending и принятие запроса в очередь допуском не считаются.
После допуска freeze не препятствует исполнению и штатному завершению этого Run, включая необходимые внутренние вызовы.
Это включает необходимые model/tool calls, retries и subcalls внутри допущенного Run, но не новые пользовательские запуски.
Новый пользовательский платный старт, доработка, ответ модели, resume/continue после границы Run требуют нового допуска.
Старый session ID, вкладка, повтор API/WS-запроса или уже пройденный UI-check не обходят политику.
Повтор idempotency key не создаёт нового исполнения и не отменяет проверку допуска для ещё не начатого pending.
Default для pending без допуска: freeze запрещает старт; проверка выполняется на границе исполнения.
Не представлять это как уже реализованный переход pending; понадобятся явно определённые отказ и безопасное состояние очереди.
Сервер — source of truth: окончательный допуск и freeze атомарно упорядочиваются на пользователя.
Если допуск раньше freeze — Run исполняется и завершается; если freeze раньше — новый допуск отклонён до вызова модели.
Область допуска фиксируется сервером по Run ID; внутренний вызов нельзя выдать за продолжение произвольного старого Run.
Все платные ingress-пути, фоновые/отложенные старты и legacy endpoints обязаны соблюдать единый инвариант.
Это требуемый контракт, а не обещание, что существующая state machine/runner уже поддерживают его.
Пользователю: «AI-доступ временно приостановлен. Обратитесь к администратору»; без причины и actor ID.
Предлагаемый default: запретить admin self-freeze сервером, чтобы случайно не лишить себя рабочего AI-доступа.
Другой администратор может заморозить admin; роль и доступ к админке не отзываются. Это не защита от злонамеренного admin.

## 6. Макеты и визуальная система — без кода

Desktop, общий header: [CoreTeams] [Основная навигация] [Администрирование] [Тема] [Аккаунт].
Под header: [Обзор | Пользователи]; H1; [Обновлено: время, зона] [Обновить].
Overview сверху вниз: [Сейчас выполняется: таблица] → [Требует внимания: период, фильтры, таблица] → [Итоги: период, N/F/U/R].
Таблица активности: [Задача / Run] [Пользователь] [Статус / этап] [Начало / прошло] [Детали].
Таблица внимания: [Исход / код] [Задача / Run] [Пользователь] [Время] [Детали]; справа read-only панель выбранного Run.
Users: [Поиск email] → [Email | Зарегистрирован | Последний визит | AI-доступ | Действие] → [Назад / страница / Далее].
Mobile: тот же header с компактным меню; две подписанные вкладки, без отдельной оболочки.
Блоки Overview в том же порядке; строки превращаются в карточки с подписями полей, детали — полноширинная панель.
Итоги — компактный список N/F/U/R с общей подписью когорты; Users — карточки, поиск и пагинация остаются сверху/снизу.
Никаких обрезанных email/ID без способа прочитать или скопировать; длинный текст переносится.
Общие typography/surface/theme tokens Shell; отдельная категориальная палитра не нужна: графиков и цветового кодирования серий нет.
Статусы прежде всего текстовые, иконки дополнительные; error и unknown различимы не только цветом; поддержка forced-colors.
Таблицы семантические; клавиатурная навигация, видимый focus, подписи кнопок, возврат фокуса после закрытия modal/panel.
Live-обновление не перехватывает фокус; новые уведомления без постоянного озвучивания всей таблицы.

## 7. Концептуальные данные/API и обновление

Admin overview читает списки Run, счётчики и metadata: server_now/as_of, границы периода, полнота, курсоры страниц.
Списки ограничены и пагинируются сервером; totals считаются по всей выборке, не по текущей странице.
Admin users читает минимальные поля и версию политики; mutation меняет freeze с expected version и idempotency key.
Отдельное admin detail чтение выдаёт только allowlist; история audit — admin-only, не расширение обычного User DTO.
Общий пользовательский DTO может сообщать лишь effective AI-access, без private reason, audit и actor.
Private reason не попадает в клиентские логи, аналитику, обычные ошибки и публичные/пользовательские события.
Все admin endpoints сохраняют AdminUser; проверка политики запуска серверная, независимо от роли UI и транспорта.

Default refresh: polling каждые 15 секунд видимой страницы, без перекрывающихся запросов; пауза в фоне, refresh при возврате.
Ручное обновление доступно; ответы старых поиска/страницы/периода не заменяют новые. Modal не сбрасывается polling.
Свежесть показывается по последнему успешному серверному снимку, а не по времени попытки запроса.
После сбоя сохраняем данные с «Не удалось обновить»; старше 45 секунд — «Данные устарели», не актуальные нули.
Retry с ограниченным backoff до 60 секунд; без нового WebSocket и без утверждений о гарантированном realtime.
Empty: «Нет выполняющихся запусков», «Проблем за выбранный период не найдено», «Пользователи не найдены» только после успеха.
Initial loading — skeleton без цифр; initial error — описание/повтор вместо пустой таблицы; partial — отдельная пометка блока.
401: прекратить polling, убрать приватные данные, предложить вход; 403: убрать admin-данные, показать «Недостаточно прав».
Ошибка mutation сохраняет введённую причину в открытой форме, не показывает успех; повтор после проверки актуального состояния.

## 8. Совместимость, обратимость и проверка дизайна
