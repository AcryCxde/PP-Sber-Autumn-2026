# ADR и mapping: точечные изменения на ревью

Аудитория: Арина, Дима, Филипп и Катя. Статус: **PROPOSED / REVIEW_REQUIRED**.
Это указатель на разрешённый к публикации пакет ревью, не вторая спецификация API.

## Уже подтверждено владельцем WEB

- Основной пользовательский интерфейс — React B; A остаётся reference.
- Ответ на текущий вопрос продолжает тот же Run.
- Явная доработка завершённого результата создаёт новый Run прежнего проекта,
  сохраняя документ и историю версий.
- Центральное сохранение выполняется через gateway/адаптер storage, не runner.
- Сохранение версии и отдельное одобрение пользователя — разные подтверждения.

Источник: [опубликованные ответы WEB 16–21](https://github.com/pokatyusha/project-harness/blob/36a041aa6724421768e28e5a5278d2e98283d69a/handoff/2026-10-15/contracts/web-answers-16-21.md)
и [пакет ADR/mapping](https://github.com/pokatyusha/project-harness/blob/36a041aa6724421768e28e5a5278d2e98283d69a/handoff/2026-10-16/contracts-review/README.md).
Это не принятие всех DTO/ошибок владельцами gateway и storage.

## Что изменить в исходных документах после согласования

| Тема | Предлагаемая правка | Кто сверяет реализацию |
|---|---|---|
| Ответственность за запись | Runner создаёт локальный checkpoint и metadata; gateway получает bytes точной версии и вызывает storage. Локальный checkpoint не равен центральному сохранению | Дима + Арина; Филипп — доступ к томам и runtime |
| Terminal | `outcome_unknown` — последнее терминальное событие Run; позднее подтверждение относится к операции сохранения и не переоткрывает Run, не добавляет `run.completed` после terminal | Дима + Арина |
| Состояния/события/вопросы | Использовать исходный events.v0 и `waiting_for_input`; явно описать проекцию в WEB, полный questions[]/answers map и `unknown_fork` | Дима + Катя, существующий runner — исходная сторона |
| Версии/approval | Stable document, immutable version; rework после completed — новый связанный Run. Approval — отдельная идемпотентная запись/receipt конкретной сохранённой версии вне закрытой Run-ленты | Арина + Дима + Катя |

Точные поля, обязательность, авторизация, error codes, конфликты и readback должны
быть согласованы в исходном контракте соответствующей границы. Здесь они не
назначаются по предположению и не объявляются реализованными.

## Чеклист ревью

- [ ] Арина: запись/чтение, receipt, project/Run binding, immutable bytes/версии,
  отдельный approval, миграции и восстановление; реализация, а не только ADR.
- [ ] Дима: канонический transport/events mapping, auth/ownership, команды/ack,
  idempotency, safe retry, terminal и подключение storage.
- [ ] Катя: mapping B без потери онбординга/файлов/вопросов/команды/плана,
  явные неподтверждённые состояния, отдельные saved/approved.
- [ ] Филипп: совместимые SHA, безопасная конфигурация, persistent volumes,
  runtime/WSS, restart и воспроизводимый общий прогон.
- [ ] Каждая сторона: ответ `принимаю / нужна правка / не реализовано`,
  точный раздел, SHA, выполненная проверка и оставшийся блокер.

Отсутствие ответа не означает согласия. Новых дедлайнов этот документ не вводит.
