## Приёмочный чеклист общего сценария

Сначала заполнить [manifest и handoffs](integration.md). Выполнять с синтетическими
несекретными данными, реальным runner и реальным storage, не fixture.

- [ ] Открыть именно React B: онбординг и пример до первой задачи.
- [ ] Создать проект, передать контекст и реальные bytes вводного файла; проверить hash.
- [ ] Согласовать роли/план; выполнить проверку ролей и этапов на стороне сервера.
- [ ] Запустить Run, получить события от настоящего runner.
- [ ] Получить весь questions[], отправить ответы и продолжить тот же Run.
- [ ] Пережить disconnect/retry/unknown_fork без второго Run/команды/версии.
- [ ] Получить результат и дождаться durable receipt точной версии; неподтверждённое
  сохранение не отображается успешным.
- [ ] Скачать bytes/ZIP той же версии, проверить hash/размер и готовым validator состав.
- [ ] Отдельно одобрить версию; terminal Run не меняется, approval читается повторно.
- [ ] Явно доработать completed-результат: новый Run, прежний документ/история сохранены.
- [ ] Перезапустить сервисы, повторно открыть проект и прочитать версии/receipt.
- [ ] Чужой actor/project/artifact/version не раскрывает данные и не меняет состояние.
- [ ] Неизвестные usage значения остаются unknown; измеренные нули не подменяются.

## Шаблон протокола

```text
Время и среда:
URL/безопасный способ доступа (без секретов):
Manifest полных SHA/образов/config-version:
WEB-вариант и версия API:
Синтетический project / Run / command / operation / version:
Шаг / ожидание / факт / PASS|FAIL|NOT_RUN:
Безопасная ссылка на лог/тест/receipt/hash:
Блокер / существующая задача / ответственный / следующее действие:
Ограничения и что не проверено:
Проверка Кати и отдельное разрешение merge конкретным PR: НЕ ПОЛУЧЕНО
```

Реальные секреты и персональные исследовательские данные не публиковать.
DEPLOYMENT_READY подтверждается техническими доказательствами, затем отдельно
нужны согласие и baseline конкретного участника для сравнения с привычным способом.
Интерфейсный smoke, кабинетный анализ и реальный пользовательский E2E — разные виды
проверок; отсутствие времени/результата нельзя заменять нулём или «успехом».
