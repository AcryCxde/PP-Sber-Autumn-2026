# Архитектура прототипа CoreTeams

Актуализировано: 1 октября 2026. Здесь описано существующее демо, а не целевая production-архитектура. Пользовательский интерфейс v9 и API-стенд — два отдельных контура. Между ними нет интеграции.

## 1. Актуальный интерфейс v9

```text
Браузер: public/v9/index.html + style.css + app.js
  ├─ контекст, ответы → правила сценария → предложение команды
  ├─ таймер симуляции → вопрос / подготовленный результат → согласование
  ├─ localStorage["coreteams-v9"] → проекты, версии, отзывы, метаданные файлов
  └─ Blob → скачивание результата Markdown

Node.js server.js → выдача HTML, JS, CSS, шрифтов, изображений и видео для v9
Автономный HTML → те же ресурсы встроены в один файл; сервер не требуется
```

Входы `/`, `/v9` и `/v9/` открывают v9. `build-v9.mjs` создаёт два одинаковых файла: `CoreTeams-прототип-v9.html` и `CoreTeams-прототип.html`.

- Сценарии: курс, книга, бизнес-идея, другая задача. Выбор направления явный, не AI-классификация.
- Роли задаются правилами в `teamFor`; выбор продвижения добавляет маркетолога. Настоящие агенты CTF не создаются и не вызываются.
- Состояния UI: `draft → working → waiting → working → review`; после одобрения следующего этапа снова `working`, после последнего — `ready → done`. Доработка возвращает в `working` и создаёт новую версию.
- Это локальные состояния проекта, не события серверного Run. Проценты, время и кредиты демонстрационные.
- Файлы сохраняются только как названия/метаданные; содержимое не читается и не загружается. Текст контекста и уточнения включаются в шаблонный результат.
- Данные существуют в этом браузере. Нет серверной синхронизации, межустройственного профиля, отправки почты или фонового исполнителя. При недоступном хранилище показывается предупреждение.
- Форма входа — макет: почта и пароль не сохраняются. Лимит трёх проектов проверяется локально и не является механизмом защиты.
- v9 не обращается к `/api/*` и не подключается к SSE.

## 2. Отдельный демонстрационный API

```text
API-клиент / test/server.test.js
  → server.js: /api/projects/:projectId/runs/...
  → имитация Run через таймер
  → data/state.json: проекты, запуски, события, артефакты
  → JSON-история / SSE / скачивание Markdown
```

API демонстрирует постановку Run, смену состояний и порядок `artifact_saved` перед `completed`. Есть исходы `failed`, `unknown` и `limit_reached`. Состояние `waiting` из v9 в этот API не интегрировано.

| Метод и путь | Назначение |
|---|---|
| `GET /api/projects` | Список демонстрационных проектов |
| `GET/POST /api/projects/:projectId/runs` | Список / запуск имитации |
| `GET /api/projects/:projectId/runs/:runId/events` | История событий |
| `GET /api/projects/:projectId/runs/:runId/stream` | SSE новых событий без автоматического воспроизведения истории |
| `GET /api/projects/:projectId/runs/:runId/artifact` | Подтверждённый демонстрационный Markdown |

Идентичность берётся из `x-demo-user` либо значения по умолчанию. Клиент может подставить этот заголовок: проверка владельца — учебный пример, **не аутентификация и не безопасная изоляция**. JSON-файл не является надёжной многопользовательской БД; ключи идемпотентности не изолированы по пользователю/проекту. Стенд привязан к `127.0.0.1` и не предназначен для публичного API-доступа.

## 3. Прежний интерфейс и архив

`/v8` выдаёт прежний UI из `public/index.html`, `public/app.js`, `public/app.css` и `public/extra.css`. В нём сохранены демонстрационная операторская и её макеты метрик. Это не операторская v9: общей базы проектов и отзывов нет. Клиентская проверка демо-кода и `sessionStorage` не обеспечивают реальные администраторские права.

Исторические HTML v2–v7 находятся в [archive/html](archive/html/). Они не служат источником актуальной сборки. В GitHub сгенерированные HTML помечены `linguist-generated`, чтобы ревью начиналось с исходников.

`build-standalone.mjs` — исторический сборщик прежнего UI; он пишет в общий `CoreTeams-прототип.html`. Для текущей версии используйте только `npm run build:standalone` (вызывает `build-v9.mjs`).

## 4. Связь со спецификациями

[Пакет эпика 2.5](epic-2.5-v3/README.md) описывает проектируемую модель доступа, состояния Run, границы событий и ограничения v1. Это требования и материалы для приёмки, не доказательство их реализации в v9. Локальные `ready/done` не означают серверную долговременную запись или выполнение CTF.

До подключения реального исполнителя нужно согласовать авторизацию и владение объектами, контракт событий и артефактов, паузы/возобновление, идемпотентность, хранение файлов и проверку доступности ролей. Затем заменить таймерную симуляцию адаптером, сохранив пользовательский путь.

## 5. Граница доказательств

- `test/v9-scenarios.test.js`: правила четырёх сценариев, роль маркетолога, совместимость старых проектов, содержимое шаблонов и версии.
- `verify-v9.mjs`: синтаксис JS в HTML, встроенные ресурсы, равенство двух актуальных HTML. Не браузерный end-to-end тест.
- `test/server.test.js`: отказ для чужого демонстрационного проекта при стандартном заголовке и отсутствие `completed` при `unknown`. Не доказывает защищённость API.
- Ручная проверка интерфейса описана в [UX-V9.md](UX-V9.md).

CTF/executor, gateway, production-авторизация, RBAC, облачное хранилище, биллинг, анализ файлов и сквозные серверные события в v9 не подключены.
